# Calendar module — current state

Migrated out of the root `CLAUDE.md` (2026-08-15) so this detail only loads when you're actually working under `src/features/calendar/` or `functions/src/shared/calendar/`. Same "facts, not standards" rule applies — if your change alters a fact here, update it in the same commit.

- **The executive Calendar is shipped, and its backend was written fresh (2026-08-13).** `src/features/calendar/` was built during the Apps Script era, so `createCalendarEvent`/`cancelCalendarEvent` never existed as Cloud Functions and `calendarEvents` had no rules block. Both callables now live in [functions/src/shared/calendar/events.ts](functions/src/shared/calendar/events.ts) — the path `calendar.types.ts` already pointed at. Notes: `startAt`/`endAt` are stored as Firestore `Timestamp`s (the client sends ISO strings; the read layer converts back), and conflict detection filters the `endAt` side in memory because Firestore allows only one range-filtered field per query.
- **Google Calendar sync shipped 2026-08-18 (HR_OPERATIONS.md §9.3/§14.4), replacing the old `syncStatus: 'skipped'` stub.** [functions/src/shared/calendar/googleSync.ts](functions/src/shared/calendar/googleSync.ts) calls the Calendar REST API (`events.insert`/`patch`/`delete`/`freeBusy`) with a service-account JWT from **`google-auth-library`** — promoted from a firebase-admin transitive to a direct dep, deliberately **instead of `googleapis`**, which is enormous next to the four endpoints this needs. Secret `GOOGLE_CALENDAR_SA_KEY` (the whole service-account JSON as one string) plus an `integrations/googleCalendar` doc holding `calendarId`; **with either missing every sync call is a silent no-op**, so an unprovisioned environment behaves exactly as it did before. Events are now written `syncStatus: 'pending'` and pushed inline from `createCalendarEventInternal` (§9.3-F02's 30-second target), with `syncCalendarEvents` (`*/15 * * * *`, §9.3-F07) sweeping anything still `pending`/`failed` — 50 per run, no cursor. §14.4's dedup is literal: patch when `gcalEventId` is stored, insert when it isn't, and fall back to insert on a 404 so an externally-deleted event doesn't wedge. `cancelCalendarEvent` deletes the remote copy (§9.3-F06). The `companyEvent` approval-resolved handler does **not** push inline — it runs inside the approval Firestore trigger, which would have to declare the secret; the 15-minute sweep picks it up instead. §9.3-F03 widens the conflict check with a `freeBusy` query, and a Google failure there returns `[]` so the in-app check stays authoritative.
- **Calendar improvements** (HR_OPERATIONS.md gap-closing pass, 2026-08-15): type/department/outlet/owner filters on `CalendarAgendaPage.tsx` (owner resolved via the existing `subscribeToDirectory`); a Month view (`CalendarMonthView.tsx`, new) behind an Agenda/Month `Tabs` toggle, backed by a new `subscribeToEventsInRange()` in `calendarService.ts` — same single-range-field shape `subscribeToUpcomingEvents` already uses, so no new index. **`companyEvent`-type events now route through the Approval Engine before they're confirmed** — the first real design change of the four: `CalendarEventStatus` gained a `'pendingApproval'` value and `CalendarEvent` gained `approvalRequestId`, `createCalendarEventInternal` (`functions/src/shared/calendar/events.ts`) submits via `submitApprovalInternal` when `eventType === 'companyEvent'` instead of writing `eventStatus: 'confirmed'` directly, a new `'calendar/companyEvent'` route (single-step `generalManager`) sits in `shared/approval/routes.ts` next to the previously-unused `'hr/contract'` route, and `functions/src/shared/calendar/index.ts` registers a `registerApprovalResolvedHandler('companyEvent', ...)` mirroring `hr/recruitment/index.ts`'s `'requisition'` handler exactly. No `firestore.rules` change — the existing read predicate doesn't discriminate by `eventStatus`.
