# Settings module — current state

Migrated out of the root `CLAUDE.md` (2026-08-15) so this detail only loads when you're actually working under `src/features/settings/` or `functions/src/settings/`. Same "facts, not standards" rule applies — if your change alters a fact here, update it in the same commit.

- **Communication Settings moved here from Communications (2026-08-17)**, at `/settings/communications` — [src/features/settings/pages/CommunicationSettingsPage.tsx](src/features/settings/pages/CommunicationSettingsPage.tsx) + `communicationSettingsService.ts`, backed by [functions/src/communications/communicationSettings.ts](functions/src/communications/communicationSettings.ts)'s `updateCommunicationSettings` (self-service, `requireActiveUser` only, no permission string — every user manages only their own `communicationSettings/{uid}` doc). It rewires its own back-link to `/settings` and its chat-channel import to `@/features/communications/chat/chatService` instead of a relative path, but the backend module/collection/permission names are unchanged. Unlike `RolePermissionsPage`, this is **not** gated to super admins — `RolePermissionsPage.tsx` renders a link to it above its own `isSuperAdmin` early-return so every signed-in user can reach it from `/settings`, even though the rest of that page is admin-only. v1 enforcement is UI-only: muting a channel in Team Chat just dims/hides it client-side, no server-side notification suppression yet.
- **Settings ships Roles & Permissions at `/settings` (2026-08-15), closing a gap every module since HR Inventory has had to flag by hand.** `roles/{roleId}` docs used to be written exactly once — seeded from the server-only `ROLE_PERMISSIONS` map (`functions/src/lib/organization.ts`) the first time a role was claimed by `registerUser` — so every new permission string needed manual Firestore edits to reach existing role docs (including `roles/superAdmin`). The one new callable, `updateRolePermissions` ([functions/src/settings/updateRolePermissions.ts](functions/src/settings/updateRolePermissions.ts)), fixes that: it upserts a role's `permissions` array, following the exact `setJobDescriptionAccess`/`setSopAccess` upsert shape. **Gated by role identity (`requireSuperAdmin`), not a permission string** — `PERMISSIONS.ROLES_MANAGE` stays unused on purpose, since a permission string that gates editing permissions would be circular. `permissions` is validated for shape only (non-empty strings, deduped) rather than against a full whitelist — `functions/src/lib/permissions.ts` is a deliberate *subset* mirror (only strings actually `requirePermission`-checked server-side), not the complete ~50-string catalog that lives in `src/constants/permissions.ts`; growing it into a full mirror for this one caller would be new duplication with no other consumer, so `requireSuperAdmin` is the trust boundary instead. `firestore.rules` for `roles/{roleId}` needed no change (`allow read: if isSignedIn(); allow write: if false` already covered it — Admin SDK writes aren't rules-checked anyway). [src/features/settings/pages/RolePermissionsPage.tsx](src/features/settings/pages/RolePermissionsPage.tsx) is gated by `useRole().isRole('superAdmin')` rather than `PermissionGuard`, same reasoning; it groups `PERMISSIONS` (`src/constants/permissions.ts`) by module at render time instead of a hand-maintained grouping map, so new permission strings show up automatically. **This manages what a role can do, not who has which role** — there is still no admin UI to assign a role to a specific account (`changeRole`/`assignOutlet`/`activateUser` etc. from `AUTHENTICATION.md` §18 remain unbuilt); granting someone `superAdmin` for the first time is still a direct Firestore/Console operation outside the app. **The superAdmin row is read-only (2026-08-28)**: `requirePermission`/`requireAnyPermission` bypass entirely for `superAdmin` (root `CLAUDE.md`'s 2026-08-15 note), so its `roles/superAdmin` doc was always visibility/audit-only — but the page used to let an admin toggle and save its checkboxes as if they mattered. `RolePermissionsPage.tsx` now disables every checkbox and the Save button when `roleId === ROLES.SUPER_ADMIN` (it's also the default selection), with an inline note explaining why. Every other role is unaffected — still fully editable exactly as before.
