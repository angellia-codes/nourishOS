# Documents module — current state

Migrated out of the root `CLAUDE.md` (2026-08-15) so this detail only loads when you're actually working under `src/features/documents/` or `functions/src/documents/`. Same "facts, not standards" rule applies — if your change alters a fact here, update it in the same commit.

- **The Documents module ships two sub-modules: Job Descriptions and the SOP Library (2026-08-14).** `/documents` is no longer a `<ModulePlaceholder>` — its index is a hub ([src/features/documents/pages/DocumentsHomePage.tsx](src/features/documents/pages/DocumentsHomePage.tsx)) with a card per sub-module. Job Descriptions lives at `/documents/job-descriptions` ([src/features/documents/jobDescriptions/](src/features/documents/jobDescriptions/)) with `new`, `access` and `:jobDescriptionId/edit` beneath it, backed by four callables in [functions/src/documents/jobDescriptions.ts](functions/src/documents/jobDescriptions.ts); the SOP Library is the same four routes and four callables one level over at `/documents/sop-library` ([src/features/documents/sopLibrary/](src/features/documents/sopLibrary/), [functions/src/documents/sopLibrary.ts](functions/src/documents/sopLibrary.ts)), against the `sops` collection with `departmentId`/`sopNumber`/`topic`/`driveUrl` and **no `roleId`** — an SOP belongs to a department, not a position. Content in both is curated by hand by the super admin, so the shipped state is two empty registers. Several firsts live here: **`systemSettings/jobDescriptionAccess` is the first runtime-editable config doc** (an allowlist of role ids written by `setJobDescriptionAccess`; `systemSettings/sopAccess` is its independent twin) and the reason `firestore.rules` now contains **its first cross-document `get()`** — module read access can't ride on a custom claim if it's editable at runtime. Both are matched by literal doc id so the sibling `*NumberSequences` counters stay in the deny-all, and before a doc exists its `get()` yields null and only `isElevated()` roles can read (closed by default, on purpose). The SOP Library also drops most of `documents.md` §6 — no version history, approval workflow, tags, categories, search or PDF preview; it is the browse-by-department register only, its departments come from `src/constants/organization.ts` (14) rather than §6's 10, and `sopNumber` is free text with no uniqueness check (one curator). **`requireSuperAdmin` ([functions/src/lib/rbac.ts](functions/src/lib/rbac.ts)) is the first role-based server gate** — every other callable checks permission strings, but `superAdmin` is absent from `ROLE_PERMISSIONS` and its role doc was hand-seeded, so a new `jobDescriptions.manage` string would 403 on a fresh install. Two deviations: `docs/modules/documents.md` §4/§20 has no Job Descriptions section or collection, and the PDF is an **external URL on the doc** rather than a `files` record queried by `resourceType`/`resourceId` (the PDFs already live in the company's Drive; nothing is uploaded to Storage). The link is `new URL()`-parsed server-side and restricted to http(s) because it renders into an `<a href>`.
- **Company Forms + Templates** (FEATURE_SPECIFICATIONS.md pass, 2026-08-15): both are curated "title + external link" registers, same shape as SOP Library, so they share one collection-picking implementation ([functions/src/documents/resources.ts](functions/src/documents/resources.ts), `resourceKind: 'form' | 'template'`) instead of duplicating SOP Library's four-callable shape twice. Gated by `documents.publish` — an existing permission string with no caller until now (already granted to `hrManager`/`marketing`). Unlike Job Descriptions/SOPs there's no runtime access-list doc; every signed-in user can read. The spec's "Approval Workflow" sub-feature for Company Forms would mean a generic dynamic form-submission engine — out of scope, noted as a deviation, same kind of scope-down SOP Library already made against its own spec.
