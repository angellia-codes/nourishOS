# Operations module — current state

Migrated out of the root `CLAUDE.md` (2026-08-15) so this detail only loads when you're actually working under `src/features/operations/` or `functions/src/operations/`. Same "facts, not standards" rule applies — if your change alters a fact here, update it in the same commit.

- **Operations is shipped end to end.** Real pages under `src/features/operations/*/pages/` are mounted at `/operations/lost-found`, `/operations/incidents`, `/operations/work-orders`, `/operations/checklists/{opening,closing}`, and `/operations` (a hub, see below), backed by `functions/src/operations/{lostFound,incidentReports,dailyUpdates,workOrders,checklists}/` and their `firestore.rules` blocks. Three deliberate deviations from `docs/modules/{lost-and-found-report,incident-report,daily-updates}.md` carry over conceptually into whatever ports these next, made for consistency with what was already shipped rather than gaps: (1) none of the three store an `attachments: string[]` array inline — they follow the existing convention (Employee/Appraisal/PatrolLog) of querying `files` by `resourceType`/`resourceId` instead; (2) Incident Reports routes by `assignedToRole` (a role string) rather than an arbitrary uid picked from that role; (3) Daily Updates tags Task docs (`tags: ['dailyUpdate']`) instead of adding `TASK_TYPE.DAILY_UPDATE` to the shared enum, matching the "no module-specific task types" rule `src/types/task.types.ts` already documents — `daysOpen`/`escalationLevel`/`carryForwardFromTaskId` were added to `Task` as optional fields only. (WhatsApp was out of scope when this shipped; the Fonnte adapter landed 2026-08-18 and the three scheduled jobs now opt in — see the WhatsApp bullet below.)
- **Work Orders** (FEATURE_SPECIFICATIONS.md pass, 2026-08-15): `functions/src/operations/workOrders/` closes a comment in `createIncidentReport.ts` that literally said "no Work Orders backend exists yet." `createWorkOrderInternal` (same extraction precedent as `createCalendarEventInternal`) is now the one write path — the incident report's inline doc write was replaced with a call to it (equipment-failure incidents still auto-create a linked work order). Lifecycle `open → assigned → inProgress → completed → closed` is one `updateWorkOrderStatus` callable gated by a different permission per transition (`workOrders.assign`/`.update`/`.complete`, mirroring `expenseRequests.pay`'s separation of approving vs disbursing) — those three permission strings already existed in `src/constants/permissions.ts` and were already granted to `engineering`/`barLeader` in `ROLE_PERMISSIONS`, just never enforced server-side until now (the mirror was missing from `functions/src/lib/permissions.ts`). `WorkOrderDetailPage.tsx` has a "Photos" card — `FileUpload`/`FileList` against `resourceType: 'workOrder'`, the same generic `files` convention every other module uses; no backend or rules change needed, since `firestore.rules`'/`storage.rules`' `files` blocks are already resourceType-agnostic.
- **Work Orders reworked 2026-08-19** against the four requirements raised for the module: (1) **photos** — `FileUpload` gained a `camera` prop (a second input with `capture="environment"`, ignored by desktop browsers), and the detail page splits attachments into **before** (`resourceType: 'workOrder'`) and **after** (`'workOrderAfter'`) cards; the create form stages photos client-side and uploads them once the callable returns the id, the same create-then-attach order Security Patrol uses. (2) **outlet/department** are now on the create form as a cascading `<Select>` pair and stored on the document — `createWorkOrder` validates the pair against `OUTLET_DEPARTMENTS`, the same validated-override shape Lost & Found / Incidents / Daily Updates got in the 2026-08-15 revision pass. (3) **flow**: new permission `workOrders.create` (both mirrors) granted to the shared `LEADER` array plus `hrManager`/`finance`/`generalManager`/`director`/`purchasing`/`engineering`, so a department leader can raise a request without holding `workOrders.assign` — that is what the create callable required before, which meant only engineering, purchasing and barLeader could file one; an engineer **accepts** by moving to `assigned` with no `assignedTo`, which defaults to the caller rather than adding a second callable; `inProgress` now requires a note, appended to a `progressNotes[]` log (`{note, by, at}`); and **completion is gated server-side on an after photo existing** — `updateWorkOrderStatus` queries `files` for `resourceType: 'workOrderAfter'` and throws `failed-precondition` if there is none, with the UI mirroring the rule so the button explains itself. (4) **escalation**: new scheduled `checkWorkOrderEscalations` (07:15 WITA, right after `checkDailyTaskEscalations`) walks work orders still `open`/`assigned`/`inProgress` — 1 day escalates to `engineering`, 3 days to `generalManager`, in-app plus WhatsApp. Idempotent via `escalationLevel` exactly like the daily-updates sweep, and it takes the **highest** crossed threshold so a long-stale work order does not climb one rung per day. Standing caveat applies: existing `roles/{roleId}` docs need `workOrders.create` added by hand. Note the escalation targets a **role** — "Restaurant & Maintenance Manager" is a position (`positions.ts`), not a role, so engineering is the level-1 recipient.
- **Opening/Closing Checklists** (FEATURE_SPECIFICATIONS.md pass, 2026-08-15): item lists are a hardcoded code table (`src/constants/checklist.ts` / `functions/src/lib/checklist.ts`), not an admin-editable doc — the spec asks for completion tracking and photo attachments, not a template-authoring UI. One doc per outlet+day with a **deterministic id** (`${outletId}__${date}`), so there's no query and no composite index; `saveChecklistProgress` toggles one item at a time as staff work through the list. Photo attachments are one shared `FileUpload` for the whole day's checklist rather than per-item — a deliberate scope-down. New permission `checklists.record`, added to the shared `LEADER` array and `hrManager` (existing `roles/{roleId}` docs need it added by hand, same standing caveat as every module before this).
- **Operations became a hub** (`OperationsHomePage.tsx`) once Work Orders and Checklists landed alongside the existing three sub-modules — same precedent HR and Documents already set. Daily Updates moved from the bare `/operations` index to `/operations/daily-updates`.
- **Project Management shipped 2026-08-18 (HR_OPERATIONS.md §9.8) — a 6th Operations card, and the last PRD module with no code at all.** `projects` (new collection, both `collections.ts` mirrors) holds one doc per project: the board column, owner, dates, priority, and an **embedded `milestones` array** — not a sub-collection, since §9.8 asks for milestone tracking and a milestone has no lifecycle beyond its project (capped at 25 so one read stays one read). Four callables in [functions/src/operations/projects/](functions/src/operations/projects/): `createProject` (drafts), `submitProject`, `updateProject`, `moveProjectColumn`. **A project reaches the board only through the Approval Engine** — the new `'operations/project'` route (hrManager → generalManager, §9.10's "Project Request") and its `registerApprovalResolvedHandler('project', …)` are the only writers of `column: 'todo'`, the same "approval owns the first transition" rule `vacancyStage` enforces for requisitions. Project tasks are ordinary Task Engine tasks (`sourceModule: 'operations'`, `referenceId: projectId`, `tags: ['project']`) — **no `TASK_TYPE` addition**, matching the Daily Updates precedent. New permissions `projects.read`/`create`/`manage` (both mirrors; `LEADER` gets read+create per §7.2's "Own Projects", GM/HR get manage) — same standing caveat: existing `roles/{roleId}` docs need them added by hand. The board (`ProjectBoardPage.tsx`) is five columns of cards with the column change made from the detail page's `<Select>`, not drag-and-drop — the same no-new-dependency call `CandidatePipelinePage.tsx` made.
- **Escalations, the compliance alert and the daily digest now also go out over WhatsApp** (§9.12-F06/F07/F11) — `checkDailyTaskEscalations`, `sendComplianceAlerts` and `sendDailyDigest` pass `whatsapp: true` and declare `secrets: [FONNTE_TOKEN]`. See `src/features/hr/CLAUDE.md` for the adapter itself.
- **Outlet/department become overridable on Lost & Found, Incident Reports, and Daily Updates (revision pass, 2026-08-15)**: all three previously derived `outletId`/`departmentId` purely server-side from the caller's own profile ("never from input," per `createIncidentReport.ts`'s own comment) — correct for the common case, but wrong for staff who work across outlets (drivers, roving security/HR, multi-outlet managers). All three now accept an **optional override** from the client, validated server-side against the org chart (`OUTLET_DEPARTMENTS`, the same source `registerUser`/`createEmployee` already validate against) and defaulting to the caller's own when omitted — not a blank trust boundary, a validated one. Daily Updates' outlet/department fields flip from read-only display text to a real cascading `<Select>` pair; Lost & Found and Incident Reports gain a new outlet field that wasn't on the form at all before. (Expense Requests got the same treatment — see `src/features/finance/CLAUDE.md`.)
