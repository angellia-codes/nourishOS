# Communications module — current state

Migrated out of the root `CLAUDE.md` (2026-08-15) so this detail only loads when you're actually working under `src/features/communications/` or `functions/src/communications/`. Same "facts, not standards" rule applies — if your change alters a fact here, update it in the same commit.

- **Communications ships Announcements and Tasks, and `users` is now readable by every signed-in user (2026-08-15).** `/communications` is a hub ([src/features/communications/pages/CommunicationsHomePage.tsx](src/features/communications/pages/CommunicationsHomePage.tsx)); Announcements lives at `/communications/announcements` with `new`, `:announcementId` and `:announcementId/edit`, backed by five callables in [functions/src/communications/announcements.ts](functions/src/communications/announcements.ts), and Tasks at `/communications/tasks` (`new`, `:taskId`) is **frontend-only** over the Task Engine that had shipped with no surface at all — `addTaskComment` ([functions/src/shared/tasks/taskComments.ts](functions/src/shared/tasks/taskComments.ts)) is the one callable it added, and `createTask`/`assignTask`/`completeTask`/`cancelTask` keep their creator-or-assignee authorization rather than gaining `requirePermission` checks (five internal callers depend on them). Things worth knowing before touching it: **`audienceUids` is the load-bearing field** — `firestore.rules` fails a whole list query if one returned document fails its read rule, and "outletIds is empty OR contains mine" is not expressible as a query, so `publishAnnouncement` resolves outlet/department/role targeting to concrete uids once and both the rule and the feed query key off that array (drafts have it empty, archiving clears it, which is what removes an announcement from every feed); `taskComments` denormalises `taskParticipants` for exactly the same reason. **Broadcast (`communications.md` §13) is not a separate collection or callable** — it is `category: 'emergency'` plus `publishNow`, gated by the new `announcements.broadcast` permission. **The `users` read rule widened from HR-and-above to any signed-in user** so a department leader can use the task assignee picker (§19 says they may assign tasks); the doc holds only work email, name, role, department, outlet and status. `subscribeToParticipantOptions` moved out of `calendarService.ts` into [src/services/shared/userService.ts](src/services/shared/userService.ts) as `subscribeToDirectory`, since two features now need it. New permissions `announcements.create`/`announcements.broadcast` were added to `ROLE_PERMISSIONS`, so — as with recruitment — **existing `roles/{roleId}` docs need the strings added by hand, and `roles/superAdmin` needs all three or a super admin gets 403 on create/publish.** Dropped from `communications.md`: Team Chat, Direct Messages, Activity Feed, Mentions and Communication Settings (their collections stay in the deny-all); the §9 Notification Center, because `NotificationBell`/`NotificationPanel` already cover it; §5's rich-text editor (plain text, `whitespace-pre-wrap`), its optional Review step, and scheduled publication; individual-user audience targeting; and §6's Accept/Waiting/Verified/Closed task stages, which the Task Engine still doesn't persist.
- **Pending decision, deferred by request (2026-08-15)**: a Communications sub-module for issuing a formal per-employee notice tied to a Disciplinary Record (distinct from the HR-only `disciplinaryActions` records shipped in `src/features/hr/CLAUDE.md`) — scope not yet decided.
