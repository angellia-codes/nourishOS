# Communications module — current state

Migrated out of the root `CLAUDE.md` (2026-08-15) so this detail only loads when you're actually working under `src/features/communications/` or `functions/src/communications/`. Same "facts, not standards" rule applies — if your change alters a fact here, update it in the same commit.

- **Communications ships Announcements and Tasks, and `users` is now readable by every signed-in user (2026-08-15).** `/communications` is a hub ([src/features/communications/pages/CommunicationsHomePage.tsx](src/features/communications/pages/CommunicationsHomePage.tsx)); Announcements lives at `/communications/announcements` with `new`, `:announcementId` and `:announcementId/edit`, backed by five callables in [functions/src/communications/announcements.ts](functions/src/communications/announcements.ts), and Tasks at `/communications/tasks` (`new`, `:taskId`) is **frontend-only** over the Task Engine that had shipped with no surface at all — `addTaskComment` ([functions/src/shared/tasks/taskComments.ts](functions/src/shared/tasks/taskComments.ts)) is the one callable it added, and `createTask`/`assignTask`/`completeTask`/`cancelTask` keep their creator-or-assignee authorization rather than gaining `requirePermission` checks (five internal callers depend on them). Things worth knowing before touching it: **`audienceUids` is the load-bearing field** — `firestore.rules` fails a whole list query if one returned document fails its read rule, and "outletIds is empty OR contains mine" is not expressible as a query, so `publishAnnouncement` resolves outlet/department/role targeting to concrete uids once and both the rule and the feed query key off that array (drafts have it empty, archiving clears it, which is what removes an announcement from every feed); `taskComments` denormalises `taskParticipants` for exactly the same reason. **Broadcast (`communications.md` §13) is not a separate collection or callable** — it is `category: 'emergency'` plus `publishNow`, gated by the new `announcements.broadcast` permission. **The `users` read rule widened from HR-and-above to any signed-in user** so a department leader can use the task assignee picker (§19 says they may assign tasks); the doc holds only work email, name, role, department, outlet and status. `subscribeToParticipantOptions` moved out of `calendarService.ts` into [src/services/shared/userService.ts](src/services/shared/userService.ts) as `subscribeToDirectory`, since two features now need it. New permissions `announcements.create`/`announcements.broadcast` were added to `ROLE_PERMISSIONS`, so — as with recruitment — **existing `roles/{roleId}` docs need the strings added by hand, and `roles/superAdmin` needs all three or a super admin gets 403 on create/publish.** §5's rich-text editor (plain text, `whitespace-pre-wrap`), its optional Review step, and scheduled publication; individual-user audience targeting; and §6's Accept/Waiting/Verified/Closed task stages (Task Engine still doesn't persist them) all remain dropped.
- **Team Chat, Activity Feed, and Mentions shipped (2026-08-17); two pieces moved out of Communications the same day by request.** Direct Messages, File Sharing as its own surface, attachments/reactions/search in chat, and @Department/@Role mentions are still out — not requested, collections/UI for the first two stay deny-all/unbuilt.
  - **Team Chat** is text-only — [functions/src/communications/chat.ts](functions/src/communications/chat.ts) (`createChannel`, `sendMessage`). **No channel list page** — `/communications/chat` (`ChatChannelListPage`) was built and then removed by request; the header's `ChatBell`/`ChatPanel` ([src/components/layout/ChatBell.tsx](src/components/layout/ChatBell.tsx)) is now the only channel picker, same toggle shape as `NotificationBell`/`NotificationPanel` (icon button → anchored dropdown → outside-click overlay closes it), merging the same three scoped channel subscriptions the old list page used. `/communications/chat/new` and `/communications/chat/:channelId` still have real pages — a header dropdown can't host actual message composing, so channel creation and conversations are reached by clicking through the panel, not folded into it. A channel's membership is implicit from the caller's `departmentId`/`outletId` custom claims against the channel's `scopeType` (`company`/`department`/`outlet`), not an explicit members array — same "empty/company == everyone" shape Announcements' audience uses, collapsed to one dimension since a channel only ever targets one scope. `chatMessages` denormalises `scopeType`/`departmentId`/`outletId` from the parent channel at send time, same reason `taskComments`/`audienceUids` do. New permissions `chat.send` (→ `BASE`, every role) and `chat.manageChannels` (→ `LEADER`, plus `director`/`generalManager`/`hrManager` by hand since they build off `BASE` directly, not `LEADER`) — same "existing `roles/{roleId}` docs need the strings added by hand" gotcha as Announcements.
  - **Activity Feed has no page of its own** — a dedicated `/communications/activity` page was built and then removed by request. `activityFeed` (a new collection, **not** `auditLogs`, which stays deny-all-to-clients and isn't feed-shaped) is read only by `TeamActivityWidget` on the dashboard ([src/features/dashboard/CLAUDE.md](../dashboard/CLAUDE.md)), styled as a non-clickable `Timeline`/`TimelineItem` list — the same embedded-audit-log presentation `EmployeeProfilePage.tsx` uses, not a browsable page. [functions/src/shared/activity/activity.ts](functions/src/shared/activity/activity.ts)'s `recordActivityInternal` mirrors `sendNotificationInternal`'s shape — called from inside another module's already-authorized callable, after its `recordAuditEvent`. Wired into 5 hook points so far: `AnnouncementPublished`, `TaskCompleted`, `EmployeeJoined` (including bulk imports, since it hooks `createEmployeeInternal`), `TrainingCompleted`, `SopPublished` (Documents has no draft/publish workflow, so "adding an SOP" is the hook). Company-wide, `isSignedIn()`-only read rule — no audience scoping. Extensible by design: adding another hook point elsewhere is one `recordActivityInternal(...)` call, nothing else to touch.
  - **Mentions** surface through the header notification bell like any other notification (`type === 'mention'`) — no dedicated inbox page (the Notification Center page idea was rejected the same way the Activity Feed page was). [functions/src/shared/activity/mentions.ts](functions/src/shared/activity/mentions.ts)'s `recordMentionsInternal` is shared by `sendMessage` (chat) and `addTaskComment` (tasks), the two free-text surfaces with an autocomplete, and sets each mention notification's `actionUrl` straight to the source message/comment. `mentions` is a durable log collection with a real rules block but no reader UI. `MentionAutocomplete` ([src/features/communications/chat/components/MentionAutocomplete.tsx](src/features/communications/chat/components/MentionAutocomplete.tsx)) is the one shared frontend piece — a plain absolutely-positioned `<div>` dropdown, no portal/Dialog (this codebase has neither). @User only; @Department/@Role are deferred.
  - **Communication Settings moved to the Settings module** — it's account-level configuration, not a Communications record. See [src/features/settings/CLAUDE.md](../settings/CLAUDE.md).
- **Employee Communication shipped 2026-08-19, closing the pending sub-module decision that had been deferred since 2026-08-15.** `/communications/employee` (`new`, `:recordId`, `:recordId/edit`) implements `docs/modules/employee_communication.md`. The scope decision was **extend, not add**: it writes to the existing HR `disciplinaryActions` collection rather than the spec's own `communicationRecords` (§19), because that record already held the same 6-value ladder and description, and a second collection would have meant HR filing every SP1 twice or writing sync logic between the two. The two HR pages under `src/features/hr/disciplinary/` were **deleted** — their whole feature set (type, description, investigation notes) is a subset of the new detail page — and the employee profile's card now links here. It lives in Communications rather than HR because the employee is one of the audiences and `/hr/*` is HR/GM/Director-only (`/communications` has no `RoleRoute`, which is what makes an employee-facing record page possible at all).
  - **Two hard constraints from the Approval Engine shaped the design.** Steps are keyed by **role string only**, so employee acknowledgement **cannot be an approval step** — the only role a floor employee holds is `staff`, which would let any staff member acknowledge someone else's warning. It is `acknowledgeCommunicationRecord`, a separate callable gated on the record's own `employeeUid`, in the same spirit as `exitInterview.ts`'s acknowledgement booleans. And **"Department Head" is not a role** (it is `DEPARTMENT_ROLES[departmentId][0]`), so `'hr/employeeCommunication'` is the second conditional route in `shared/approval/routes.ts` — `buildCommunicationApprovalSteps` (`functions/src/hr/employees/communicationSteps.ts`) is a direct copy of Finance's `expenseSteps.ts` with the same three corrections (drop the requester's own role, dedupe, floor at `generalManager`), pinned by `functions/test/communication-steps.mjs` with no emulator. `returnForRevision` stays unused — rejection resets the record to `draft`.
  - **`employeeUid` and `releasedToEmployee` are the load-bearing fields**, for the same reason `audienceUids` is for Announcements: `firestore.rules` can only compare against `request.auth.uid`, so the employee's own login is resolved server-side at create, and the GM's approval flips `releasedToEmployee` — §5.5's "when released". `departmentId` is denormalized too, which is what finally allowed the department-head read branch the old rule comment said was impossible without a `get()`. **Most floor staff have no `users` doc**, so `employeeUid` is null, nothing matches, and the flow falls back to HR recording the acknowledgement on the employee's behalf with a `witnessedBy` — that is also how §35 Rule 7's "refused to sign" and "unable to sign" are documented. Statements HR transcribes from paper are flagged `enteredOnBehalf` rather than passed off as the employee's own.
  - **One new permission string, `employees.communicate`, added additively.** Reusing `employees.update` alone would have made §5.4 undeliverable: `ROLE_PERMISSIONS` grants `employees.update` to **`hrManager` only**, so no department head could raise a communication for their own team. The employer-side callables therefore take `requireAnyPermission([EMPLOYEES_COMMUNICATE, EMPLOYEES_UPDATE])` and the new string goes to `LEADER`. Because HR's existing grant is still accepted, **the usual `roles/{roleId}` hand-editing gotcha is deferred rather than triggered**: hrManager and superAdmin work untouched today, and adding `employees.communicate` to the leader role docs by hand is what later switches department-head creation on. Nothing breaks either way. Employee-side writes are identity-gated and need no permission at all. Validity is `DISCIPLINARY_VALIDITY_DAYS` (90 days verbal, 180 SP1-3, none for coaching/termination) mirrored in `functions/src/hr/employees/helpers.ts` and `src/constants/hr.ts`, overridable per record on the form — which is what satisfies §13's "configurable by HR" without a settings collection. The clock starts at acknowledgement (§35 Rule 5), and `expireCommunicationRecords` (08:00 WITA, stateless exact-day-match like `contractAlerts.ts`) flips `active` → `expired` and warns HR at 30/14/7/1 days. In-app only, no `secrets: [FONNTE_TOKEN]`.
  - **Dropped from the spec on purpose**: §24's dashboard widgets, §39's three reports, WhatsApp delivery, §15's *automatic* next-action recommendation (the fields are there; §35 Rule 4 keeps the decision with HR, so the form shows prior records and the heaviest sanction in force and stops), §22's internal-comments subcollection (`investigationNotes` already is that), and any i18n framework — §33's bilingual labels are literal `{en, id}` pairs in `employeeCommunicationFormat.ts`, because the Indonesian is what the official form says rather than a translation of the UI. §32's PDF is Tailwind `print:` variants on the detail page (declaration + the four-party signature grid appear, chrome and internal notes do not); **there is still no PDF library anywhere in this repo**. `status: 'open'` from records that predate the workflow is **not migrated** — it is a legacy value in the union, labelled "Open (legacy)", and can still be closed.
