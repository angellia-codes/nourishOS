# Security module — current state

The only feature module without one until this pass. Same "facts, not standards" rule as every other module CLAUDE.md — if your change alters a fact here, update it in the same commit.

- **Checkpoint create/edit/archive shipped (2026-08-20), closing `docs/modules/security-control-point.md` §2's two named gaps.** `createCheckpoint` was live before this — validated, audit-logged, gated on `security.manageCheckpoints` — but the permission string was granted to **no role** in `ROLE_PERMISSIONS`, so only `superAdmin` (which bypasses `requirePermission` entirely, [functions/src/lib/rbac.ts](functions/src/lib/rbac.ts)) could actually call it, and there was no UI at all: `CheckpointListPage`'s empty state used to read "ask a supervisor to add one via createCheckpoint" and `securityService.createCheckpoint` had no caller in `src/`. `updateCheckpoint` and `archiveCheckpoint` ([functions/src/security/](functions/src/security/)) are new, following the `updateSop`/`deleteSop` shape exactly — shared field validation in `helpers.ts`, `previousValues`/`newValues` on the audit event, `return handleError(error)`. `security.manageCheckpoints` is now granted to `hrManager` (and superAdmin via the bypass) — **existing `roles/hrManager` documents need the string added by hand**, via Settings → Roles & Permissions or `node functions/tools/sync-role-permissions.mjs --prefix security. --apply`; it only auto-seeds on a role's first claim.
- **Archive is soft, like every business record in this repo.** `archiveCheckpoint` sets `status: 'archived', isArchived: true` and nothing else — `lastVisitedAt`/`lastVisitedBy`/`lastAlertedAt` are untouched, so `patrolLogs` keep resolving `checkpointName` for history even after the checkpoint itself drops out of `getActiveCheckpoints`/`subscribeToActiveCheckpoints`/`checkOverdueCheckpoints`'s `where('isArchived','==','false')` filters. Re-archiving an already-archived checkpoint succeeds rather than erroring, matching `deleteSop`'s idempotent convention; `updateCheckpoint` conversely 404s on an archived checkpoint, matching `updateSop`.
- **`Checkpoint.outletId` shipped (2026-08-20) — stored and displayed only, not used to scope visibility.** `security-control-point.md` §3's outlet field is on the form and the list row now, validated server-side against `OUTLET_DEPARTMENTS`'s keys the same way `submitShiftReport` validates an outlet (`functions/src/security/helpers.ts`). **Deliberately not done:** the guard's checkpoint list is still company-wide — `getActiveCheckpoints`/`subscribeToActiveCheckpoints` have no outlet filter, so §3/§4's implied per-outlet visibility is still open. That's a materially bigger change (a new composite index, a policy for GM/superAdmin/multi-outlet guards) than "add the field", and wasn't asked for. **Checkpoints created before 2026-08-20 have no `outletId`** — the list omits the outlet label for those rather than showing `undefined`, and editing one now requires picking a real outlet before it can be saved (the field is required going forward). No backfill script exists; one modeled on `functions/tools/migrate-checklists.mjs` would be needed if existing checkpoints ever need it.
- **`checkpoint.lastVisitedByName` shipped (2026-08-20)** — `createPatrolLog` denormalizes `user.displayName` onto the checkpoint alongside `lastVisitedBy`, the same reasoning `patrolLogs.checkpointName` already used (no second read to show a name). The list's "Last patrolled …" line appends `by <name>` only when both `lastVisitedAt` and the name are present, so patrols logged before this change degrade to the old no-name form rather than erroring.
- The doc's §6 RBAC table also names a "Security Supervisor" role that does not exist in `src/constants/roles.ts` — the doc's own footnote flags this and says to verify before wiring a guard, which the create/edit/archive pass did: the permission went to `hrManager`, not to the `security` role itself, per the code comment on `PATROLS_CREATE`/`CHECKPOINTS_MANAGE` in [src/constants/permissions.ts](src/constants/permissions.ts) ("registering/editing checkpoints themselves is a supervisor action").
- **The `/security` route subtree has no `RoleRoute`** — the list and patrol-capture screens stay open to every signed-in user, same as before this pass. Only the Add/Edit buttons on `CheckpointListPage` and the archive control on `CheckpointFormPage` are gated, via `PermissionGuard`, and the callables enforce it server-side regardless of what the client hides.
- **`functions/src/lib/permissions.ts` is still missing `PATROLS_READ`** — the client constant (`src/constants/permissions.ts`) has it, no server callable checks it. Pre-existing, untouched by this pass.

- **Fire Extinguishers (APAR) shipped 2026-08-26** (`docs/modules/fire-extinguisher.md`, now v1.1), replacing the `/security/fire-extinguishers` `<ModulePlaceholder>` stub. Two new collections (`fireExtinguishers`, `fireExtinguisherInspections`, both mirrors + rules blocks + two composite indexes), four callables and two scheduled jobs in `functions/src/security/fireExtinguishers/`, four pages under `src/features/security/fireExtinguishers/`. What's worth knowing before touching it:
  - **The doc's `/operations/apar` routes are not what shipped** — everything is under `/security/fire-extinguishers`, because the nav stub was already there and the `/security` subtree has no `RoleRoute`, which is exactly what a guard mid-round needs. The doc's §9 was updated to match rather than left to rot.
  - **Two permission strings, not the doc's five.** `apar.manage` (register/edit/retire) and `apar.inspect` (record a round) are the only ones with an enforcement point; reads are rules-gated signed-in and cross-outlet, so `apar.view`/`apar.viewAllOutlets` would have checked nothing, and `apar.reportUsage` belongs with the deferred usage report. Granted to `security`+`engineering` (inspect) and `hrManager`+`engineering`+`generalManager` (manage). **Standing caveat, and here it is the difference between the module working and nobody being able to open a round**: live `roles/{roleId}` docs need them added by hand — `node functions/tools/sync-role-permissions.mjs --prefix apar. --apply`.
  - **A round is one task per outlet per month**, created by `generateMonthlyAparRounds` (1st, 06:00 WITA) with `referenceId: '${outletId}__${periodMonth}'`. That one string is the dedup key (a single equality query, so a re-run creates nothing), the round screen's source for its outlet and period, and what `parseRoundReferenceId` rejects a non-round task by. The round holds **no unit list** — the screen reads the register live, so a unit registered on the 8th appears in the round generated on the 1st.
  - **Inspection uniqueness is a deterministic doc id** (`${extinguisherId}__${periodMonth}` + `.create()`), the same trick `shiftHandovers` uses, not a query or a rules check. Duplicate submissions come back as `already-exists` with the asset code in the message.
  - **`submitAparInspection` is not one transaction**, though the doc's §6 says it is: the Work Order goes through `createWorkOrderInternal`, which owns its own audit entry and cannot join a caller's transaction. The deterministic id covers the invariant that mattered.
  - **Gauge and seal/pin failures are forced to `needsService`** server-side (§4.6) — a client asking for `resolvedOnSpot` on those is corrected, not rejected. Every failure needs a note **and** a photo, and the `photoFileId` is checked against the `files` collection rather than trusted. Self-resolved failures still record as `fail`.
  - **Shipped online-only, against the doc's own §10 ship-block on D3.** No local draft, no queue: per-unit submit means a dropped connection costs the unit in hand and the guard is told immediately. AC-3 is knowingly unmet and stays open against D3.
  - Usage/discharge reporting, the compliance dashboard and `checkOverdueAparRounds` are deferred (doc §15) — a discharge is filed today as an Incident Report plus a Work Order.
  - Test: `node functions/test/apar-inspection.mjs` (no emulator — 17 checks over the §4.6 rules and the period-key arithmetic). **The flow was never exercised end to end**: this machine has no Java, so `firebase emulators:start` could not run.
