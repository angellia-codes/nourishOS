# HR module — current state

Migrated out of the root `CLAUDE.md` (2026-08-15) so this detail only loads when you're actually working under `src/features/hr/` or `functions/src/hr/`. Same "facts, not standards" rule applies — if your change alters a fact here, update it in the same commit. The root file still holds cross-cutting architecture, RBAC, and Definition of Done.

- **The module is labelled "People" in the navigation as of 2026-08-25** (sidebar group and `HrHomePage`'s H1). Paths, the `/hr` `RoleRoute` gate and every collection name are unchanged — this is a label and a nav grouping, nothing else. The People group also lists **Positions, Recruitment and Employee Communication**, which keep their own top-level URLs (`/positions`, `/recruitment`, `/communications/employee`) precisely because they must stay outside the `/hr` role gate; the nav gates those children individually rather than gating the group. `HrHomePage` gained an Employee Communication card (removed from the Communications hub) and its Appraisal Templates card is now labelled "Appraisal".

- **`Employee` in `src/types/employee.types.ts` is the shipped shape** (mirrors what the old, now-unported `createEmployee` action used to write: `position`, `employmentStatus`, ISO-string dates). The PRD §12.1 schema (`TaxStatus`, `EmployeeCompensation`, etc.) sits below it in a clearly-marked PLANNED section — do not use those in shipped code paths yet.
- **`Employee.position` moved from free text to a validated `PositionId` (2026-08-17), closing the gap root `CLAUDE.md`'s "Departments > People" note flagged.** `POSITIONS.md` §3/§4's catalog already existed client-side as `POSITION_CATALOG`/`POSITION_LABELS` (`src/constants/positions.ts`) but nothing validated against it. New: `positionsForDepartment(departmentId)` scopes the catalog per app department (`organization.ts`'s `admin_general`/`cashier`/etc.) via a hand-curated `DEPARTMENT_POSITION_IDS` map — **not** a mechanical join on `POSITION_CATALOG[id].department`, since POSITIONS.md's own department grouping (`fbService`/`finance`/`bar`/…) is a different taxonomy that doesn't line up 1:1 with the app's operational departments. Mirrored server-side in `functions/src/lib/positions.ts` (same convention as `organization.ts`) — `createEmployee`/`updateEmployee` now reject a position outside the department's allow-list, re-checked on `updateEmployee` whenever either `position` or `departmentId` changes (a department transfer alone can orphan a previously-valid position). `EmployeeFormPage.tsx`'s Position `<Select>` follows the exact legacy-value-fallback pattern already established for Department/Outlet/Religion. Every place `Employee.position` is displayed (list/profile/exports/reports) resolves through `POSITION_LABELS[position] ?? position`, and `EmployeeImportPage.tsx`'s CSV importer resolves Position the same way it already resolved Gender/Employment Status/Contract Type (`resolveEnum` against value-or-label), scoped to the row's resolved department. This is what makes `probationReviewTrigger.ts`'s `positionId: employee.position` actually match `AppraisalTemplateSeed.positionId` for employees hired going forward — legacy employees and positions with no seeded probation template are the two remaining reasons that trigger still falls back to notifying `hrManager` instead of creating the review.
- **`DEPARTMENT_POSITION_IDS` revised the same day against an explicit 12-point per-department policy**, replacing the first pass's "every catalog entry under its POSITIONS.md heading" default. Specifics worth knowing:
  - **`trainee`/`dailyWorker` are no longer appended to every department** — they're listed explicitly, and only, under `fb_service`/`bar`/`kitchen`. ("The Bakery Kitchen" is an outlet, not a department — `OUTLET_DEPARTMENTS` staffs it from `kitchen`.) `central_kitchen`/`security`/`wholefood_retail` weren't named by the policy and keep their original (non-trainee/DW) lists unchanged.
  - **`housekeeping` is deliberately empty — confirmed with the user, not a bug.** POSITIONS.md has no Housekeeping section and the policy didn't add trainee/dailyWorker back for it, so **no position is currently selectable for that department**; registering an employee into Housekeeping is blocked until real titles exist in the taxonomy.
  - `purchasingManager`/`purchasingSupervisor` moved from `driver` to `finance_accounting`; `driver` is now exactly Driver Leader/Driver.
  - `restaurantMaintenanceManager` is now offered from **both** `fb_service` and `engineering_pomec` — the policy added it to the former without removing it from the latter.
  - Several catalog ids became unreachable from *every* department (`ceo`, `groupOperationalManager`, `operationalManager`, `runner`, `groupBarManager`, `barBack`, `assistantBarManager`, `directorOfSalesMarketing`, `socialMediaSpecialist`, `engineerCivil`, `groupHrManager`, `trainingDevelopmentSupervisor`, `groupFinancialController`, `costControl`, `arIncomeAudit`) — left in `POSITION_CATALOG`/`POSITION_LABELS` rather than deleted, since a legacy employee record may still carry one and needs it to keep resolving to a label.
- **Position scoping gained an outlet dimension the same day: `positionsForDepartment(departmentId)` → `positionsFor(outletId, departmentId)`.** `kitchen` is staffed by both `the_bakery_kitchen` and the standard restaurant outlets (`nourish_ungasan`/`nourish_uluwatu`/`nourish_berawa`), and the two outlet types split cleanly along a bakery/restaurant line — a department-only lookup can't express "only at this outlet within the department," so `OUTLET_ONLY_POSITION_IDS` (both `src/constants/positions.ts` and `functions/src/lib/positions.ts`) intersects the department list per position: **bakery-only** (Chief Baker, Chef de Partie Baker/Pastry, Cook/Baker → `the_bakery_kitchen`) and **restaurant-only** (Head Chef, Sous Chef, Chef de Partie, Demi Chef de Partie, Cook, Cook Helper → the three `nourish_*` outlets, via a shared `STANDARD_RESTAURANT_OUTLET_IDS`). `steward`/`trainee`/`dailyWorker` are deliberately unrestricted — common to both outlet types. Every call site threads outletId alongside departmentId: `EmployeeFormPage.tsx`'s Position `<Select>` (also resets on outlet change, not just department change), `EmployeeImportPage.tsx`'s CSV resolver, and `createEmployee`/`updateEmployee`'s server-side validation (`updateEmployee` re-checks position whenever `position`, `departmentId`, **or `outletId`** changes — an outlet transfer within the same department, e.g. off `the_bakery_kitchen`, can orphan a bakery- or restaurant-only title the same way a department transfer can).
- **Employee create/edit revised (2026-08-15): `preferredName` removed, Department/Outlet are real dropdowns, a Contract PDF slot, and bulk import.** `preferredName` is gone everywhere (type, both callables, form, CSV export, search, profile) — it had no other logic depending on it. Department/Outlet on `EmployeeFormPage.tsx` were plain free-text `<Input>`s (typo-prone, and `departmentId` is what `firestore.rules` uses to scope department-leader reads) — they're now cascading `<Select>`s mirroring `RegisterPage.tsx`'s `OUTLETS`/`OUTLET_DEPARTMENTS`/`optionsFor` pattern, with a legacy-value fallback so an existing bad value stays editable instead of silently blanking. `createEmployee.ts`/`updateEmployee.ts` now validate the pair against `OUTLET_DEPARTMENTS` server-side too — closing a gap `registerUser.ts` already covered but the employee callables never did. `EmployeeProfilePage.tsx` gained a distinct "Contract Document" card (`resourceType: 'employeeContract'`, PDF-only) alongside the pre-existing generic "Documents" card (`resourceType: 'employee'`) — same `FileUpload`/`FileList`/`createFileMetadata`/`deleteFile` mechanism, zero backend changes, since `resourceType` is just a string and `storage.rules`/`firestore.rules` are already resourceType-agnostic. **Bulk import** (`/hr/employees/import`, HR_OPERATIONS.md §9.1-F12, previously unbuilt anywhere in the app) follows the one existing precedent for reusing a callable's mutation logic from a second caller — `createCalendarEventInternal`'s extraction — so `createEmployee.ts` now exports `createEmployeeInternal`, and the new `importEmployees` callable loops it per row with partial-success semantics (a bad row is reported, not thrown, and the batch continues), capped at 100 rows. No permission-string mirror was duplicated for this: `src/utils/csv.ts` gained a hand-rolled `parseCsv` (no CSV library on either side, still none — this reads a template the app itself generates) and the import page resolves Department/Outlet/Gender/Employment Status/Contract Type from either their display label or raw value, since the template is filled in by hand.
- **The HR recruitment pipeline is shipped end to end (2026-08-14), and `/hr` is now a hub.** The employee register moved from the `/hr` index to `/hr/employees`; the index is [src/features/hr/pages/HrHomePage.tsx](src/features/hr/pages/HrHomePage.tsx). Four chained sub-modules live under [src/features/hr/recruitment/](src/features/hr/recruitment/) and [functions/src/hr/recruitment/](functions/src/hr/recruitment/): requisitions (`recruitments`), candidates (`candidates`, stages ST-01…ST-08), interviews (`interviews`), onboarding (`onboardingChecklists`) — twelve callables plus an `hr/requisition` approval route. Things worth knowing before touching it: **a candidate cannot exist without an approved requisition** and **`vacancyStage` is only ever set by the approval-resolved handler** in `functions/src/hr/recruitment/index.ts`, which is what makes "no vacancy before approval" true rather than merely intended; hiring (ST-06) is the one write with side effects — it counts against the requisition inside a transaction, completes it when the last opening is filled, and generates the onboarding checklist; **`createCalendarEventInternal` was extracted** from `functions/src/shared/calendar/events.ts` so `scheduleInterview` can write a calendar event without a second callable (the callable now owns only auth + audit); `createEmployee` gained an optional `candidateId` that links the new employee back to the candidate and its checklist, since **hiring deliberately does not auto-create an employee** (candidate data has no NIK, contract type or probation). Deviations from `docs/modules/employee-requisition.md` and `HR_OPERATIONS.md` §9.4: the approval chain is fixed (hrManager → generalManager) rather than adding a Director step for unbudgeted requests — `budgeted` is captured, so that is a `shared/approval/routes.ts` change when wanted; no `confidential/compensation` subdocument; no WhatsApp (§9.5) since no Fonnte adapter exists; the board moves stages via a `<Select>` rather than drag-and-drop (no new dependency). `ROLE_PERMISSIONS` gained `recruitment.read`/`recruitment.create` for the leader roles — **that only affects role docs seeded from now on**, so existing `roles/{roleId}` documents need the strings added by hand.
- **HR Inventory ships uniform & asset stock tracking at `/hr/inventory` (2026-08-15), a 5th card on the HR hub.** `docs/modules/hr.md` §12 "Employee Assets" names `employeeAssets` and an Assign/Transfer/Return-per-asset shape; this ships a **unified stock ledger** instead — item master + per-outlet (per-size, when the item tracks sizes) stock levels + an append-only movement log — because uniforms need size-level quantities a per-asset-unit model doesn't represent, and "stock tracking, movement, cost" is the ledger pattern, not an assign/return log. **`EMPLOYEE_ASSETS` stays reserved and unused.** Deliberately distinct collections — `hrInventoryItems`/`hrStockLevels`/`hrStockMovements` in [functions/src/hr/inventory/](functions/src/hr/inventory/) — from the `INVENTORY_ITEMS`/`STOCK_LEVELS`/`STOCK_MOVEMENTS`/etc. that were reserved in `src/constants/collections.ts` for a separate, much larger F&B warehouse module `docs/modules/inventory.md` used to describe (FIFO/FEFO, waste logs). **That top-level module — and Purchasing and CRM alongside it — was cut from scope on 2026-08-15**: the reserved collection names, the `/inventory`, `/purchasing` and `/crm` `<ModulePlaceholder>` routes, their `Sidebar`/`ROUTES` entries, and all three PRD docs were deleted; HR Inventory is now the only inventory concept in the app. Five callables (`createInventoryItem`, `updateInventoryItem`, `receiveStock`, `issueStock`, `transferStock`) share one transactional helper, `applyDelta` (pinned by `node functions/test/hr-inventory-stock.mjs`, no emulator needed) — every mutation runs inside `db.runTransaction`, and `transferStock` reads both outlets' stock levels before writing either (Firestore transactions forbid reads after writes), writing two linked movement docs (`transferOut`/`transferIn`) sharing a `linkedMovementId`. `category` and `hasSizes` are immutable after item creation — changing either would orphan existing `hrStockLevels` docs keyed by the old size set. No per-serial asset tracking (a laptop is a count of "laptop" stock, not an individually tagged unit) and no approval engine — permission-gated like Operations, not multi-step approved like Finance. New permissions `hrInventory.manage` (item-master curation, `hrManager` only) and `hrInventory.record` (day-to-day receive/issue/transfer, granted to `hrManager` and every outlet leader via the shared `LEADER` array) — same standing caveat as every prior module: `ROLE_PERMISSIONS` only seeds a role doc on first claim, so existing `roles/{roleId}` docs (including `roles/superAdmin`) need both strings added by hand.
- **HR ships a Reports sub-module at `/hr/reports` (2026-08-15), a 6th card on the HR hub — eight report views, zero backend changes.** Active Employee, Resigned Employee, Employee Turnover, Manning Budget, Manning Cost, Employee Activity, Budget and Cost, and Upcoming Activity and Budget (`docs/modules/hr.md` §16 names most of these as aspirational; Manning Budget/Cost/Budget-and-Cost/Upcoming are net-new, not in that list). A correction (§6.2) creates a second document for the same month since that id is taken, so it gets an auto-generated id — every query, sort and the People Report's period dropdown go through the stored `period` field via `functions/src/hr/attendance/context.ts`'s `findHeadPeriod`, never the doc id. `isCorrection: true` is only accepted against a head whose status is `approved`; a draft/rejected head was never readable to anyone (nothing to preserve a supersede trail for), so it's resubmitted via `submitAttendancePeriod` instead — no delete/edit-draft callable exists, deliberately, since the doc never asked for one.
  - **CSV taxonomy**: the nine codes (§2) and legacy alias fold (`NPL`→`UL`, `DPH`/`DPN`→`DP`, `OFF`→`DO`, §2.2 D4) live in `functions/src/hr/attendance/codes.ts` — pure, no Firestore, mirrored client-side in `src/constants/attendance.ts` (same intentional duplication as `collections.ts`/`permissions.ts`). Pinned by `node functions/test/attendance-import.mjs` (no emulator), covering the fold and every V1–V7 hard rule against the master sheet's own reference row shape.
  - **Reuse over duplication**: `ValidationIssueList` (`src/features/hr/payroll/components/import`) renders attendance's reconciliation issues directly — the `ValidationIssue` shape (severity/row/employeeNumber/code/message) is identical, so `AttendanceReconciliationReport` imports Payroll's type rather than defining a parallel one.
  - **File archival is new plumbing, not reused**: unlike Payroll (which never archives its source CSV), `importAttendancePeriod.ts` writes the raw CSV text to Storage via the Admin SDK (`getStorage().bucket().file(path).save()`) then calls `createFileMetadataInternal` — the same pattern `uploadCandidateDocument.ts` established, chosen over a client-side Storage upload first because the CSV text is already in memory server-side by the time validation passes.
  - **RBAC**: five new permission strings, `attendance.import`/`attendance.approve`/`attendance.viewAllOutlets`/`attendance.viewOwnOutlet`/`attendance.export` — `viewAllOutlets`/`export` went to the exact `canReadPayroll()` audience (hrManager/finance/generalManager/director/superAdmin), and `viewOwnOutlet` went onto the shared `LEADER` array (every outlet leader plus `outletManager`/`restaurantManager`), reusing `firestore.rules`' existing `canReadPayroll()`/`isDepartmentHead()` helpers rather than adding new ones. The doc's reserved-but-ungranted `attendance.readOwn` is deliberately not scaffolded as a constant, same call already made for `payroll.readOwn`. Approval route `'people/attendancePeriod'` is a fixed two-step HR Manager → GM chain (`shared/approval/routes.ts`, copies `'hr/contract'`'s shape). **Standing gotcha applies**: existing `roles/{roleId}` docs need all five strings added by hand or via `sync-role-permissions.mjs --prefix attendance. --apply`.
  - **Task Engine**: a new monthly `onSchedule` job, `remindAttendanceImport` (1st, 06:00 WITA), creates a reminder Task for every active HR Manager — mirrors `generateMonthlyAparRounds.ts`'s referenceId-dedup shape.
