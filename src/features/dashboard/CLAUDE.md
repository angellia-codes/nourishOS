# Dashboard module — current state

Migrated out of the root `CLAUDE.md` (2026-08-15) so this detail only loads when you're actually working under `src/features/dashboard/`. Same "facts, not standards" rule applies — if your change alters a fact here, update it in the same commit.

- **The dashboard is no longer a placeholder, and it carries the app's first approval queue (2026-08-15).** `/` is [src/features/dashboard/DashboardPage.tsx](src/features/dashboard/DashboardPage.tsx) — the `dashboard.md` §6 welcome banner plus widgets in `src/features/dashboard/widgets/`: Pending Approvals (§9), Assigned Tasks (§10), Announcements (§12), and Upcoming Calendar (2026-08-15, closing the §26 "Company calendar" wishlist item — a thin wrapper over the calendar module's existing `subscribeToUpcomingEvents`, confirmed events only, no new query shape). All read-only, top five, linking out to the pages that own the actions; **no backend changes at all** — §17's `getDashboardSummary()`/`getPendingApprovals()` aggregators are not built, since every source already has a client-readable query. The one thing worth knowing: **the approval engine routes by role, not by uid.** The live step doc carries `approverRole` (`functions/src/shared/approval/submitApproval.ts`), there is no assignee field anywhere, and the equivalent on the request (`steps[currentStepIndex].approverRole`) is an array-index lookup Firestore cannot query — so `subscribeToApprovalQueue` ([src/services/shared/approvalService.ts](src/services/shared/approvalService.ts)) queries `approvalSteps` (`allow read: if isSignedIn()`) and joins each step back to its request one read at a time. **That join only works because every `approverRole` in `routes.ts` is on the `approvalRequests` read rule's elevated list — naming an approver role outside it means updating `firestore.rules` in the same change.** superAdmin gets a separate branch: it is an override approver but never a named `approverRole`, so it queries every pending step instead and sorts client-side (no second index). Two indexes were added (`approvalSteps` approverRole+stepStatus+createdAt, `approvalRequests` requestedBy+createdAt), and `ApprovalRequest.workflowId` became optional while gaining the `steps` array — the server writes the latter and never the former, so the type had it exactly backwards. Not built: quick actions (§8), department/per-role variants (§14/§15), the §11 notifications widget (the header bell already is one), and §18's manual refresh (every widget is a live listener).
- **Team Activity and Recently Completed Tasks widgets shipped alongside the Communications module's Activity Feed (2026-08-17).** `TeamActivityWidget` reads the new `activityFeed` collection (top 5, `createdAt desc`) — it's the **only** consumer of that collection: a standalone `/communications/activity` page was built and removed by request the same day, so this widget has no `viewAllTo` and renders entries as a non-clickable `Timeline`/`TimelineItem` list (title + relative time), the same embedded-audit-log presentation `EmployeeProfilePage.tsx` uses, rather than the usual `WidgetRow` link-out pattern. `RecentlyCompletedTasksWidget` reads `taskService.subscribeToMyCompletedTasks` (`assignedTo array-contains uid` + `taskStatus=='completed'`, sorted/sliced client-side by `completedAt` rather than adding a 3rd composite index field for 5 rows) and does link out to `/communications/tasks`. Six widgets total now.
- **The widget set is role-scoped as of 2026-08-18 (HR_OPERATIONS.md §9.9/§9.13), closing the "per-role variants (§14/§15) not built" gap above.** `ROLE_WIDGETS` in `DashboardPage.tsx` maps `profile.roleId` → extra widgets; the four common ones (approvals, own tasks, announcements, calendar) stay for everyone because they're about the viewer's own work, and anything not in the map falls back to `DEFAULT_EXTRAS` (Team Activity + Recently Completed Tasks — what outlet leaders had before). Four new widgets: **ContractRenewalsDue** (§9.9's contract-60d and probation-30d rows merged, since they share a source and an urgency rule), **InterviewsToday** (today plus the rest of the week, covering both §9.9's HR "Interviews Today" and the GM's "Upcoming Interviews 7d"; reads `calendarEvents`, not `interviews`, so no new query shape), **EscalationCenter** (§9.13's colour bands are exactly `escalationLevel` 1/2/3+, already stamped by the daily-updates job — needs the new `subscribeToDailyUpdateTasks`, one `array-contains` and no index, since only elevated roles can read others' tasks it renders the `denied` state otherwise), and **ActiveProjects** (§9.9's "Active Projects Count" + "Projects At Risk" in one list, at-risk first). Still deliberately **not** built: the doc's Recruitment Funnel and Review Completion Rate rows — both already have report pages, and a widget would be a second aggregation of the same data. No backend aggregators either; every widget is still a client-side subscription.
- **Dashboard KPI Cards** (FEATURE_SPECIFICATIONS.md pass, 2026-08-15): `src/components/shared/MetricTile.tsx` is the one shared component `STYLE_GUIDE.md` names as still unbuilt — built here rather than a one-off. `KpiCardsRow.tsx` reuses the four widgets' own subscriptions for 3 of 4 tiles (Pending Approvals, Open Tasks, Announcements — zero new reads); Active Employees is the one new read, a single `getCountFromServer` aggregation (no documents fetched, no listener).
- **Active Employees tile is department-scoped for department managers (2026-08-16)** — replaces the short-lived `Departments > People` module (see root `CLAUDE.md`), which was deleted in favor of putting the number where a manager already looks. `KpiCardsRow.tsx` derives `isDepartmentManager` by checking `profile.roleId === DEPARTMENT_ROLES[profile.departmentId]?.[0]` (same leader-role convention `contractAlerts.ts` uses) and, when true, adds `where('departmentId', '==', profile.departmentId)` to the existing `getCountFromServer` query and relabels the tile "Active Employees (Dept)". Everyone else still sees the org-wide count. No backend changes — `employees` reads are already department-scoped-or-elevated in `firestore.rules`, so a leader reading their own department's count needs nothing new.
- **Active Employees tile gained a "View detail" link (2026-08-27)**, gated by the new `HR_REPORT_ROLES` export (`src/constants/roles.ts` — GM/Director/HR Manager/superAdmin, the same list `routes.tsx`'s `HR_MODULE_ROLES` now imports from, so the two can't drift). `MetricTile` (`src/components/shared/MetricTile.tsx`) gained an optional `to` prop for this — when present the whole card becomes a `<Link>` with a "View detail →" caption; every other tile call site is unaffected. Links to `/hr/reports/active-employees`, which now shows a PKWT+PKWTT/Daily Worker/On-the-Job Training/Other breakdown (`buildEmploymentStatusBreakdown`, `src/features/hr/reports/utils/`) — see `src/features/hr/CLAUDE.md`. Department managers viewing the dept-scoped tile don't get the link (they have no `/hr` access), same as before this change.
