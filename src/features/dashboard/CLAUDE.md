# Dashboard module — current state

Migrated out of the root `CLAUDE.md` (2026-08-15) so this detail only loads when you're actually working under `src/features/dashboard/`. Same "facts, not standards" rule applies — if your change alters a fact here, update it in the same commit.

- **The dashboard is no longer a placeholder, and it carries the app's first approval queue (2026-08-15).** `/` is [src/features/dashboard/DashboardPage.tsx](src/features/dashboard/DashboardPage.tsx) — the `dashboard.md` §6 welcome banner plus four widgets in `src/features/dashboard/widgets/`: Pending Approvals (§9), Assigned Tasks (§10), Announcements (§12), and Upcoming Calendar (2026-08-15, closing the §26 "Company calendar" wishlist item — a thin wrapper over the calendar module's existing `subscribeToUpcomingEvents`, confirmed events only, no new query shape). All read-only, top five, linking out to the pages that own the actions; **no backend changes at all** — §17's `getDashboardSummary()`/`getPendingApprovals()` aggregators are not built, since every source already has a client-readable query. The one thing worth knowing: **the approval engine routes by role, not by uid.** The live step doc carries `approverRole` (`functions/src/shared/approval/submitApproval.ts`), there is no assignee field anywhere, and the equivalent on the request (`steps[currentStepIndex].approverRole`) is an array-index lookup Firestore cannot query — so `subscribeToApprovalQueue` ([src/services/shared/approvalService.ts](src/services/shared/approvalService.ts)) queries `approvalSteps` (`allow read: if isSignedIn()`) and joins each step back to its request one read at a time. **That join only works because every `approverRole` in `routes.ts` is on the `approvalRequests` read rule's elevated list — naming an approver role outside it means updating `firestore.rules` in the same change.** superAdmin gets a separate branch: it is an override approver but never a named `approverRole`, so it queries every pending step instead and sorts client-side (no second index). Two indexes were added (`approvalSteps` approverRole+stepStatus+createdAt, `approvalRequests` requestedBy+createdAt), and `ApprovalRequest.workflowId` became optional while gaining the `steps` array — the server writes the latter and never the former, so the type had it exactly backwards. Not built: KPI cards (until the next bullet), quick actions (§8), activity feed (§13), department/per-role variants (§14/§15), the §11 notifications widget (the header bell already is one), and §18's manual refresh (every widget is a live listener).
- **Dashboard KPI Cards** (FEATURE_SPECIFICATIONS.md pass, 2026-08-15): `src/components/shared/MetricTile.tsx` is the one shared component `STYLE_GUIDE.md` names as still unbuilt — built here rather than a one-off. `KpiCardsRow.tsx` reuses the four widgets' own subscriptions for 3 of 4 tiles (Pending Approvals, Open Tasks, Announcements — zero new reads); Active Employees is the one new read, a single `getCountFromServer` aggregation (no documents fetched, no listener).
