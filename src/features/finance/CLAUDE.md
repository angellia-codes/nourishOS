# Finance module — current state

Migrated out of the root `CLAUDE.md` (2026-08-15) so this detail only loads when you're actually working under `src/features/finance/` or `functions/src/finance/`. Same "facts, not standards" rule applies — if your change alters a fact here, update it in the same commit.

- **Finance ships Expense Requests, and approval routes are now conditional (2026-08-15).** `/finance` is the expense register itself rather than a hub ([src/features/finance/expenses/](src/features/finance/expenses/)), backed by five callables in [functions/src/finance/](functions/src/finance/): create/update (draft, owner-only) → submit → the resolved handler → `markExpensePaid` → `closeExpenseRequest`. The engine change is the part with reach: **`APPROVAL_ROUTES` values may now be a `(context) => steps` function** — the signature `routes.ts` always said it would grow — and `finance/expenseRequest` is the first one ([functions/src/finance/expenseSteps.ts](functions/src/finance/expenseSteps.ts), ≤5M → department leader + finance, >5M → + generalManager + director). `SubmitApprovalInternalInput` gained an optional `context`; **it is assembled by the callable from the stored document, never from `request.data`** — `totalAmount` decides the chain's length, so a client-supplied total would be a client-chosen approval chain. The three HR routes stay static arrays, and the `hr/requisition` `budgeted` branch that was deferred is now a one-file change. Other things worth knowing: "Department Manager" isn't a role, so step 1 resolves from the requester's department via `DEPARTMENT_ROLES`, then the chain drops the requester's own role (self-approval is blocked by uid, so a lone kitchenLeader would stall their own request), dedupes, and floors at `generalManager`; `buildExpenseApprovalSteps` is pure and pinned by `node functions/test/expense-steps.mjs`, which needs no emulator. **`functions/src/lib/sequences.ts` is new** — `allocateYearlyNumber` was copy-pasted four times; recruitment now shares it (same doc ids and field keys, no migration), while the incident and lost & found allocators keep their own because their counter field key differs. New permission `expenseRequests.pay`, granted to `finance` only so a GM who approved cannot also disburse; `requireExpensePermission` follows recruitment's `requireRecruitmentPermission` in letting superAdmin through, so no hand-seeding is needed this time. Deviations from `docs/modules/expense-request.md` (all now corrected in that doc): items embed on the request rather than an `expenseItems` collection, receipts are `files` records queried by `resourceType`/`resourceId` rather than a `receiptFileIds` array, and resolution is an eventually-consistent trigger rather than part of the engine's transaction.
- **Expense Requests gained a second, independent field, `paymentCategory` (2026-08-27)**: `'reimbursement' | 'cashAdvance'`, orthogonal to the existing `category` (what the spend is for) — this one says how the money moves. Threaded through `createExpenseRequest`/`updateExpenseRequest` the same way `category` already was; `PAYMENT_CATEGORIES`/`validatePaymentCategory` live next to `EXPENSE_CATEGORIES`/`validateCategory` in `functions/src/finance/helpers.ts`, required with no default (matches `outletId`/`departmentId`'s "no sane default" pattern on the form). `submitExpenseRequest`'s existing generic "at least one receipt" gate (`countReceipts`, still `files` where `resourceType == 'expenseRequest'` — no new resourceType) now throws a category-aware message: "Attach an invoice…" for reimbursement, "Attach a quotation or a photo of the item…" for cash advance, and `ExpenseDetailPage.tsx`'s attachment card retitles/rehints the same way. No new permission, index, or rules block — it's a same-document field, not a new collection.
- **Outlet/department become overridable (revision pass, 2026-08-15)**: previously derived purely server-side from the caller's own profile ("never from input," per `createExpenseRequest.ts`'s own comment) — correct for the common case, but wrong for staff who work across outlets. Now accepts an **optional override** from the client, validated server-side against `OUTLET_DEPARTMENTS`, defaulting to the caller's own when omitted. Gains outlet+department fields on `ExpenseFormPage.tsx` that weren't there at all before. `ExpenseRequest.outletId`/`departmentId` turned out to already be typed — inherited from `BaseDocument`, just not re-declared — so no type gap actually existed there, only under-documentation, now fixed with a comment instead of a redundant re-declaration. (Lost & Found, Incident Reports, and Daily Updates got the same treatment — see `src/features/operations/CLAUDE.md`.)
