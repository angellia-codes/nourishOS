# Auth module — current state

Migrated out of the root `CLAUDE.md` (2026-08-15) so this detail only loads when you're actually working under `src/features/auth/` or `functions/src/auth/`. Same "facts, not standards" rule applies — if your change alters a fact here, update it in the same commit.

- **Self-service registration is shipped, against what `AUTHENTICATION.md` §5 says (2026-08-14).** The doc specifies HR-provisioned accounts and "users are **not** self-registered", but that provisioning flow has no UI or callable, so only the bootstrap superAdmin could ever sign in. `/register` ([src/features/auth/RegisterPage.tsx](src/features/auth/RegisterPage.tsx), public route) collects Full Name → Outlet → Department → Role, each dropdown narrowed by the one above it, and `registerUser` ([functions/src/auth/registerUser.ts](functions/src/auth/registerUser.ts)) writes `users/{uid}` with `status: 'active'`. `ProtectedRoute` now splits the two denial cases: **no profile → `/register`**, profile present but not active → `/unauthorized`. Notes: the org chart lives in `src/constants/organization.ts` mirrored by `functions/src/lib/organization.ts` (constants, not `outlets`/`departments` Firestore docs — nothing edits them and there is no Settings UI); `OUTLET_DEPARTMENTS` is *derived* from outlet concept type since no doc maps outlets to departments; `superAdmin` is absent from every `DEPARTMENT_ROLES` list so it can't be self-granted; and `registerUser` seeds `roles/{roleId}` from `ROLE_PERMISSIONS` (RBAC.md §4/§5) the first time a role is claimed, since only `roles/superAdmin` was ever created by hand.

- **The registration Role dropdown became the org role ladder on 2026-08-29.** `DEPARTMENT_ROLES` now lists one RBAC role per HR job title (44 roles, up from 18) instead of RBAC.md §4's coarse tiers. Three things to know:
  - **Nine titles reuse an existing role id and only changed label**, so `firestore.rules`' hardcoded role lists and every existing `users/{uid}` document keep working untouched: `marketing` = Creative & Marketing Manager, `engineering` = Engineering MEP, `hrManager` = Jr. HR Manager, `finance` = Chief Accountant, `purchasing` = Purchasing Manager, `security` = Security Supervisor, `wholefoodLeader` = Wholefood Manager, plus `restaurantManager`/`wholefoodCashier` unchanged. **The other four leader titles did not keep this shortcut**: later the same day, `floorLeader`/`barLeader`/`kitchenLeader`/`bakeryLeader` were renamed to `restaurantSupervisor`/`barManager`/`headChef`/`chiefBaker` (id and value both), and `outletManager`/`staff` were removed outright rather than just left unoffered — see the root `CLAUDE.md`'s "Current state" section for the full blast radius (`firestore.rules`, `ROLE_PERMISSIONS`, the new `OUTLET_LEAD_ROLE` map, and `functions/tools/migrate-role-ids.mjs` for live data).
  - **Role selection is outlet-scoped, not department-scoped.** `rolesFor(outletId, departmentId)` (`src/constants/organization.ts`, mirrored in `functions/src/lib/organization.ts`) intersects `DEPARTMENT_ROLES` with a new `OUTLET_ONLY_ROLES`, the same shape `positions.ts`'s `OUTLET_ONLY_POSITION_IDS` already had: the `kitchen` department carries both ladders because The Bakery Kitchen staffs it, so the three baking titles resolve only at `the_bakery_kitchen` and the six line-cook titles only at the three restaurant outlets; `wholefood_retail` offers Manager/Supervisor only at `wholefood_ungasan` (Uluwatu and Berawa are cashier-only). `registerUser` validates through the same function — a department-only check would let a Chief Baker register at a restaurant. `JobDescriptionFormPage` still reads `DEPARTMENT_ROLES` directly (no outlet in scope there), so it offers the department's full superset.
  - **New roles resolve to three permission tiers**, `LEADER` (unchanged) plus new `SUPERVISOR` and `RANK_FILE` consts in `functions/src/lib/organization.ts`. `SUPERVISOR` deliberately omits `incidents.read` and `hrGeneralAdmin` deliberately omits `employees.read`: `firestore.rules` gates both collections on hardcoded role lists, so the string alone would grant a page that then reads nothing. The one new role added to those rules lists is `restaurantMaintenanceManager` (Engineering/POMEC department head) — `isLeader()`, the three department-scoped `employees`/`disciplinaryActions`/`appraisals` branches, `incidentReports` and `workOrders`. Existing `roles/{roleId}` documents need no edit: no shipped role's permission set changed, and `registerUser` seeds each new role's document the first time someone claims it.
