# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

NourishOS is an internal operational platform for Nourish Group Indonesia, a multi-outlet F&B company — a React SPA frontend backed by a single Google Apps Script Web App ([apps-script/src/Code.gs](apps-script/src/Code.gs)), using a Google Sheet for data and Google Drive for files. It migrated off Firebase (Auth/Firestore/Cloud Functions/Storage) on 2026-08-11 to cut hosting cost; that migration is **in progress**, not complete — see "Current state" below before assuming any given backend action exists. It is in early milestone development. Implemented today: **HR appraisal** (including an AI-insights UI whose backend isn't ported yet), **HR employee database**, **Security patrol/checkpoints**, and **Operations** (Lost & Found, Incident Reports, Daily Updates) — all shipped as frontend pages, but see below for which of their backend actions actually work post-migration. Every other module (Finance, Purchasing, Inventory, CRM, Documents, Communications, Reports, Settings) is mounted as a `<ModulePlaceholder>` route stub.

PWA support (manifest, service worker) is **planned but not built** — there is no `vite-plugin-pwa` yet. Treat it as a plain Vite SPA today; don't claim or rely on offline/installable behavior until that lands.

## Environment

Development happens on Windows 11 with PowerShell as the shell. Write commands in PowerShell syntax (`;` chaining, `$env:VAR`, no heredocs into bash).

## Commands

Frontend (repo root):

```
npm run dev      # Vite dev server on http://localhost:5173
npm run build    # tsc (typecheck) then vite build — fails on any type error
npm run preview  # serve the production build
npm run lint     # ASPIRATIONAL — eslint is not installed and has no config; this fails today
```

Apps Script backend (`apps-script/`, single `Code.gs` file, deployed via [`clasp`](https://github.com/google/clasp)):

```
npm install    # installs clasp (the only devDependency)
npm run login  # opens a browser, authorizes clasp against your Google account (one-time)
npm run push   # uploads src/ to the Apps Script project — does NOT redeploy the live Web App
npm run deploy # clasp deploy — cuts a new deployment version; only this makes pushed changes live at the /exec URL
npm run open   # opens the project in the Apps Script editor (needed for one-time setup, Script Properties)
```

There's no build/typecheck step for it — `Code.gs` is plain JavaScript that the Apps Script V8 runtime executes directly; it's outside the root `tsc` project and isn't type-checked at all. See [apps-script/README.md](apps-script/README.md) for one-time spreadsheet/Drive provisioning (run `setupSpreadsheetAndDrive` from the Apps Script editor) and Script Properties setup.

There is **no test runner configured** — do not assume `npm test` exists or invent test commands. Verification means: `npm run build` passes at the root, and you exercised the affected flow in `npm run dev`. There is no Apps Script emulator — dev always talks to whatever's actually deployed at `VITE_APPS_SCRIPT_URL` (real Sheet, real Drive files, shared with anyone else pointed at the same deployment).

Copy `.env.example` → `.env.local` and set `VITE_APPS_SCRIPT_URL` (the Web App's `/exec` URL, from `clasp deploy`) and `VITE_GOOGLE_CLIENT_ID` (a Google OAuth web client ID for the Google Identity Services token-client flow). Both are required: [src/services/appsScript/client.ts](src/services/appsScript/client.ts) and [src/services/appsScript/googleAuth.ts](src/services/appsScript/googleAuth.ts) throw immediately if either is missing at build time, which — because the throw is unconditional once Vite inlines the var as `undefined` — surfaces to the user as a generic "Unable to connect. Please try again." on sign-in with no other clue. If you see that error on a deployment, check the deployment's env vars first (e.g. Vercel project settings), not just `.env.local`.

## Architecture

### Client reads, actions write

The single most important rule carries over from the Firebase era, now enforced by convention rather than security rules, since Apps Script Web Apps have no rules engine: **clients never write directly to the Sheet.** Every mutation goes through a registered action in `Code.gs`'s `ACTIONS_` map; the client only ever calls the generic `collection.list`/`collection.get` actions for reads.

- **Frontend → backend:** call actions via `callFunction<TResponse>(name, payload)` ([src/services/api/callFunction.ts](src/services/api/callFunction.ts)) — same name and signature as the Firebase era, only the transport changed underneath: it now calls `callAction()` ([src/services/appsScript/client.ts](src/services/appsScript/client.ts)), one `fetch` POST to the Apps Script Web App URL per call, body `{action, payload, sessionToken}`, envelope back `{success, message, data}` or `{success:false, code, message, details?}` — Apps Script Web Apps always answer HTTP 200 (`ContentService` has no status-code control), so success/failure is signalled in the body, never the HTTP status. Reads go through [src/services/firestore/queries.ts](src/services/firestore/queries.ts) and `subscriptions.ts` (directory/file names kept only for caller compatibility — there's no Firestore involved) — `subscribeToDocument`/`subscribeToCollection` poll `collection.get`/`collection.list` every 10s instead of using `onSnapshot`; `queryDocuments`'s constraints are applied client-side by `applyConstraints` after the full collection is fetched.
- **Backend action shape:** every entry registered via `registerActions_({ 'name.here': { handler(payload, user), public?, authLevel? } })` in `Code.gs`. `handleAction_` resolves `user` from the session token through `requireActiveUser_` (mirrors the old `requireActiveUser`) unless the action is `public: true` (only `auth.loginWithGoogle`) or `authLevel: 'session'` (only `auth.me`, which must resolve a user before their account is necessarily active). Throw `AppError_(code, message, details)` for failures — `errorEnvelope_` turns it into the `{success:false, ...}` body; anything else thrown becomes a generic `internal` error, logged server-side. Call `recordAuditEvent_(...)` after a mutation (mirrors `recordAuditEvent`). `files.upload`/`files.delete` are the canonical ported example of this shape end-to-end.
- **Only six actions are registered today**: `auth.loginWithGoogle`, `auth.me`, `collection.list`, `collection.get`, `files.upload`, `files.delete`. Adding a real per-module action (e.g. a proper `createEmployee`) means writing its `registerActions_` entry directly in `Code.gs` — there's no per-file/per-module split yet; the whole backend is one file, sectioned schema → setup → store → errors → audit → auth → files → api (see the file's own header comment). Use the generic CRUD helpers already there (`createDoc_`, `getDoc_`, `updateDoc_`, `listRows_`, `findRowById_`) rather than reading/writing sheet ranges directly, and `withLockedDoc_` (a `LockService`-based stand-in for a Firestore transaction: lock → read → mutate → write → unlock) for anything that needs read-then-write atomicity.

### RBAC

Authorization no longer rides on a token claim — there's no equivalent of Firebase custom claims. Every action call re-verifies the signed session token (`verifySessionToken_`: HMAC-SHA256 over a base64 `{uid, exp}` payload, keyed by the `SESSION_SECRET` Script Property, 12h expiry, stateless — no server-side revocation) and re-reads the live `users` row (`requireActiveUser_`, mirrors the old `requireActiveUser`), then would check `roles/{roleId}`'s `permissions` array via `requirePermission_` — today that's only actually called from `files.delete`'s owner-or-override check, since no other ported action does permission-gated logic yet. On the client, `AuthProvider` ([src/contexts/AuthProvider.tsx](src/contexts/AuthProvider.tsx)) polls `auth.me` on mount and every 60s (there's no realtime channel — see `ME_POLL_INTERVAL_MS`) and pushes profile/permissions into the Zustand auth store; `refreshAuthState()` ([src/contexts/authSession.ts](src/contexts/authSession.ts)) is shared between that poll loop and `useAuth().signIn`/`signOut` so a fresh sign-in reflects immediately instead of waiting for the next poll tick. Route protection (`ProtectedRoute` + `RoleRoute` under [src/routes/](src/routes/), component-level `PermissionGuard`) is unchanged in shape — it still reads permissions off the auth store, just populated from a different source now.

**Known gap, restated from "Current state":** the only read path (`collection.list`/`collection.get`) doesn't call `requirePermission_` or apply any department/outlet/role scoping — any active user can read any collection in full. Don't rely on reads being scoped; if a page needs role-restricted data today, that restriction exists only in the UI, not the backend.

### Shared "engines" — mostly not ported

The Firebase-era `functions/src/shared/` engines (approval, task, notifications, file storage) were deleted along with the rest of `functions/`. **Only file storage has a real port**: `files.upload`/`files.delete` in `Code.gs`, writing to Drive instead of Firebase Storage (same `/{module}/{resourceType}/{resourceId}/` folder convention as `file_storage.md` §6 describes, soft-delete only — no retention job exists yet). The approval engine, task engine, and notifications have **no equivalent in `Code.gs` yet** — `withLockedDoc_` exists as plumbing for the approval engine's eventual port but nothing calls it yet. Don't assume `submitApprovalInternal`, `createTaskInternal`, `sendNotificationInternal`, or `notifyUsersByRole` exist anywhere in this codebase — they're gone, recoverable only from git history before commit `05474c9`.

### Frontend structure

Feature-first under [src/features/](src/features/)`<module>/` (pages, components, hooks, services per feature). The router ([src/routes/routes.tsx](src/routes/routes.tsx)) mounts unbuilt modules as `<ModulePlaceholder>`. `src/components/ui/` is a small shadcn-style primitive set (`components.json`, `class-variance-authority`, `tailwind-merge`); `src/components/shared/` is app-level shared components. Global state is Zustand stores in [src/store/](src/store/) (`authStore`, `themeStore`, `toastStore`, `uiStore`). Path alias `@/` → `src/` (configured in both `vite.config.ts` and `tsconfig.json`).

### Intentional duplication

`src/constants/` (e.g. `collections.ts`, `permissions.ts`, `roles.ts`) is now mirrored by hand in **two** other places, since `Code.gs` is a separate non-npm runtime that can't import from `src/`: the `COLLECTIONS` object at the top of [apps-script/src/Code.gs](apps-script/src/Code.gs), and the `roles` Sheet tab itself (seeded with empty structure by `setupSpreadsheetAndDrive`; actual role→permissions rows have to be entered by hand in the Sheet UI, since that data lived in live Firestore `roles/{roleId}` docs, never a repo constant). This duplication is deliberate and flagged in `Code.gs`'s own header comment — when you change a collection name, permission string, or role, **update all three.**

### Frontend conventions worth keeping in mind

- UI is built from the primitives in `src/components/ui/` plus `src/components/shared/EmptyState`. **There is no Dialog/Modal** — multi-step or confirm flows are separate routed pages, not modals. `Button` has no `asChild`/Slot support — use `useNavigate()` + `onClick`, not `<Button asChild><Link>`.
- Static `/new`-style routes must be registered before `/:id` param routes in the same children array to avoid the param route swallowing them.
- Gotcha: a `const` narrowed by an early-return guard (`if (!source) return ...`) does **not** stay narrowed inside a closure (event handler, callback) defined later in the same component when the variable came from `useState` or `.find()` — TS re-widens it to possibly-`undefined` inside the closure. Extract a plain local (`const id = source.id`) right after the guard and reference that inside the closure instead of the original variable.

## Definition of done

A change is finished only when all of these hold:

1. `npm run build` passes at the root with **zero errors**. The tree is green; keep it green.
2. If you touched `apps-script/src/Code.gs`: `clasp push` succeeds and you exercised the changed action(s) against the pushed code. There's no separate typecheck/build step for it (plain JS, no `tsc`) — but remember `clasp push` alone does **not** update the live `/exec` URL; you also need `clasp deploy` (`npm run deploy` in `apps-script/`), or your change is invisible to anyone using `VITE_APPS_SCRIPT_URL`.
3. If you added or renamed a collection, permission, or role: update all three of `src/constants/`, the `COLLECTIONS` object in `apps-script/src/Code.gs`, and (for a new role) the `roles` Sheet tab.
4. Any new action follows the canonical skeleton — resolve `user` via `requireActiveUser_`/`authLevel` → mutate via the `createDoc_`/`updateDoc_`/`withLockedDoc_` store helpers → `recordAuditEvent_` → return plain data (wrapped in `successEnvelope_` by `handleAction_`) — is added via `registerActions_({...})` in `Code.gs`, and the client reaches it only through `callFunction`.
5. Behavior implemented from a spec carries a doc-section citation comment (`// API.md §7` style), matching the existing convention — but see "Documentation is the source of truth" for which docs are currently stale.
6. You exercised the affected flow in `npm run dev` against the live Apps Script Web App (`VITE_APPS_SCRIPT_URL`) — there is no emulator and no test suite to lean on; a broken action fails for real, for everyone hitting that deployment.
7. This file's "Current state" section is updated if your change altered any fact in it.
8. Commit messages follow Conventional Commits going forward: `type(scope): summary` (e.g. `feat(hr): ...`, `fix(approval): ...`, `docs: ...`). History before July 2026 is mixed — match the convention, not the history.

## Gotchas

- `clasp push` uploads code but does **not** redeploy the live Web App — you also need `clasp deploy` (or `npm run deploy` in `apps-script/`) for a change to take effect at the `/exec` URL `VITE_APPS_SCRIPT_URL` points to. Pushing without deploying is the "I fixed it but it's still broken in the browser" trap.
- Missing `VITE_APPS_SCRIPT_URL` or `VITE_GOOGLE_CLIENT_ID` doesn't fail the build — `getWebAppUrl()`/`getClientId()` only throw when actually called, and since Vite inlines a missing env var as `undefined` at build time, the minifier collapses the whole function to an unconditional `throw`. The symptom in the browser is every sign-in attempt failing instantly — no Google popup ever opens — with the generic "Unable to connect. Please try again." from [LoginPage.tsx](src/features/auth/LoginPage.tsx). If you see that, check the deployment's env vars (e.g. Vercel project settings), not just `.env.local`.
- Script Properties (`SPREADSHEET_ID`, `DRIVE_ROOT_FOLDER_ID`, `SESSION_SECRET`, `ANTHROPIC_API_KEY`) live in the Apps Script project's Project Settings, not in any checked-in file — `npm run open` in `apps-script/` to view/edit them. `setupSpreadsheetAndDrive` sets the first three once and refuses to run again if `SPREADSHEET_ID` is already set (idempotency guard, to avoid orphaning a spreadsheet/Drive folder); `ANTHROPIC_API_KEY` has to be added by hand and isn't used by anything yet (see the appraisal-insights gotcha below).
- `collection.list` always returns the **entire** collection — `applyConstraints` filters/sorts client-side after the fetch, not server-side. A collection growing past a few thousand rows will make every screen that lists it slower and heavier, not just one query (`Code.gs`'s own header comment flags this as the ceiling to watch).
- `strict` TypeScript is on for the frontend project; the build fails on any type error. `apps-script/src/Code.gs` is plain JavaScript and isn't type-checked at all.
- `npm run lint` fails with "eslint is not recognized" — eslint is not in `devDependencies` and there is no config file, even though the `lint` script itself references real eslint flags. `npm run build` (tsc + vite) is the quality gate until lint is actually scaffolded.
- The Anthropic-powered appraisal-insights feature (`generateAppraisalInsights`, used `@anthropic-ai/sdk` + an `ANTHROPIC_API_KEY` secret) was deleted along with `functions/` and has **not** been ported to `Code.gs`. The HR appraisal AI-insights UI currently has no working backend behind it — don't assume it works because the UI renders.
- Session tokens are self-issued and stateless (signed `{uid, exp}`, 12h expiry) — there's no server-side revocation list. Deactivating a user (`status` ≠ `'active'`) takes effect on their *next* action call (`requireActiveUser_` re-reads the live row every time), but an already-issued session token keeps verifying successfully until it naturally expires; there's no way to force-invalidate one early.
